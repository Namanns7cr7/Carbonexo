Carbonexo · EcoTrack architecture walkthrough

Carbonexo Internals Three processes, one request path, one database

A Next.js app talks over HTTP to a Spring Boot API, which talks over JDBC to PostgreSQL. Nothing in the browser ever touches the database. This traces one activity log from a click to a row and back.

Client
Next.js 14
:3000 · App Router · TS strict
React Server/Client components, Tailwind, Framer Motion. Holds no secrets — only a JWT in memory and a refresh token in localStorage.
API
Spring Boot 3.3
:8080 · Java 17 · Maven
11 REST controllers under /api, stateless JWT security, Hibernate/JPA, Flyway, Gemini + Vision + GCS clients.
Data
PostgreSQL 16
:5432 · db/user ecotrack
21 tables, UUID primary keys, audit columns, soft delete. Schema owned by Flyway migrations, not by Hibernate.
01 — the request path

One activity log, click to row

This is the whole system in one trace. A user on the Track page logs a 12 km car trip. Every hop below is a real file in this repo, in execution order.

1
app/app/track/page.tsx

A page calls the store, not the network

UI components never call fetch. They pull actions off the useCarbon() hook, so the page has no idea whether the write will land in Postgres or in localStorage.

2
lib/store.tsx

The store picks a backing data source

One branch decides everything downstream: signed in, so the action goes to the API and the reducer is updated from the response. Signed out, and the same reducer runs against seeded demo state persisted to the browser.

if (isAuthenticated()) {
  // → REST, Postgres is the source of truth
  await createActivity({ category, label, co2Kg, activityDate });
} else {
  // → reducer only, persisted under STATE_STORAGE_KEY
  dispatch({ type: 'ADD_LOG', payload: entry });
}
3
lib/api/activities.ts → lib/api/client.ts

A typed wrapper, then the one shared client

Each domain gets a thin typed module; all of them funnel into apiFetch. That single choke point attaches the bearer token, refreshes it on a 401 behind a mutex so parallel requests only refresh once, and converts any non-OK response into a typed ApiError.

export async function createActivity(data: CreateActivityRequest) {
  return api.post<ActivityLogResponse>('/api/activities', data);
}

// client.ts — every call passes through here
headers['Authorization'] = `Bearer ${accessToken}`;
const res = await fetch(`${BASE_URL}${path}`, { ...options, headers });
4
com.ecotrack.security.SecurityConfig → JwtAuthenticationFilter

The filter chain turns a token into a principal

The chain is stateless — no sessions, CSRF disabled, CORS driven by ecotrack.cors.allowed-origins. Everything outside /api/auth/**, Swagger and the health actuators requires a valid bearer JWT. The filter parses it and puts a UserPrincipal into the SecurityContext.

5
com.ecotrack.carbon.ActivityLogController

Controller validates, scopes to the user, maps to an entity

@Valid @RequestBody rejects bad payloads before any code runs. The user id comes from the security context, never from the request body — that is what stops one account writing rows for another. Then plain setters build the entity and repo.save is called.

@PostMapping
public ResponseEntity<ActivityLogResponse> create(@Valid @RequestBody ActivityLogRequest req) {
    UUID userId = SecurityUtils.currentUserId();   // from the JWT, not the body
    ActivityLog log = new ActivityLog();
    log.setUserId(userId);
    log.setCo2Kg(BigDecimal.valueOf(req.co2Kg()));
    log.setActivityDate(LocalDate.parse(req.activityDate()));
    repo.save(log);
    return ResponseEntity.status(HttpStatus.CREATED).body(toResponse(log));
}

The repository is an interface with no implementation

Spring Data generates the class at startup. save, findById and friends come free; method names are parsed into queries; anything awkward gets explicit JPQL. There is no hand-written SQL and no DAO layer in this codebase.

Entity becomes SQL on a pooled connection

Hibernate translates the entity's field-to-column mapping into an INSERT, borrows one of at most 10 pooled connections, and sends it. JPA auditing has already filled created_at / created_by; Postgres then enforces its own rules on the way in.

8
database/migrations/V1__baseline_schema.sql

The database has the last word

Constraints live in the schema, not only in Java. A category outside the five allowed values, or a unit that is not km/kWh/item, is rejected by Postgres even if application validation were bypassed. An ON DELETE CASCADE ties the row to its user, and a trigger maintains updated_at.

category      VARCHAR(20) NOT NULL
                  CHECK (category IN ('travel','food','electricity','shopping','waste')),
co2_kg        NUMERIC(10,3) NOT NULL,
user_id       UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
deleted_at    TIMESTAMPTZ

CREATE TRIGGER trg_activity_logs_updated BEFORE UPDATE ON activity_logs
    FOR EACH ROW EXECUTE FUNCTION set_updated_at();
9
ActivityLogResponse (a Java record) → JSON → 201 Created

Entities never leave the building

The controller maps the saved entity into a DTO record before serialising, so internal columns like deleted_at, created_by and bill_id stay server-side, and BigDecimal is narrowed to a JSON number the TypeScript interface expects. The store merges the response and React re-renders.

02 — the database connection

How Postgres is actually wired in

Five separate mechanisms, often confused for one. Connection, schema ownership, object mapping, query generation, and where the connection details come from in production.

Mechanism 1 · connection

A JDBC URL and a Hikari pool

Spring Boot sees spring.datasource.* and the postgresql driver on the classpath, and builds a DataSource at startup. Every value is an env-var override with a local-dev default, so no connection string is ever committed.

# backend/src/main/resources/application.yml
spring:
  datasource:
    url: ${DB_URL:jdbc:postgresql://localhost:5432/ecotrack}
    username: ${DB_USER:ecotrack}
    password: ${DB_PASSWORD:ecotrack}
    hikari:
      maximum-pool-size: ${DB_POOL_MAX:10}
Mechanism 2 · schema ownership

Flyway owns the schema; Hibernate is told to keep out

On boot, Flyway reads database/migrations, checks its history table, and applies anything new in version order — V1 baseline through V9 prompt templates. The critical line is ddl-auto: none: Hibernate will neither create nor alter nor even validate types. One place defines the schema, and it is checked into git.

  jpa:
    hibernate:
      ddl-auto: ${JPA_DDL_AUTO:none}   # schema owned by Flyway
    open-in-view: false
    properties:
      hibernate.jdbc.time_zone: UTC
  flyway:
    enabled: true
    locations: ${FLYWAY_LOCATIONS:filesystem:../database/migrations}
    baseline-on-migrate: true
Mechanism 3 · object mapping

One annotated class per table, with a shared base

BaseEntity is a @MappedSuperclass, so it contributes columns without being a table of its own: the UUID primary key plus the four audit columns. AuditingEntityListener populates them on save — and the DB trigger from hop 8 maintains updated_at regardless, which means a direct psql update stays correct too.

@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseEntity {
    @Id @GeneratedValue(strategy = GenerationType.UUID)
    private UUID id;
    @CreatedDate @Column(name = "created_at", updatable = false) private Instant createdAt;
    @LastModifiedDate @Column(name = "updated_at") private Instant updatedAt;
}

@Entity @Table(name = "activity_logs")
public class ActivityLog extends BaseEntity {
    @Column(name = "co2_kg", nullable = false) private BigDecimal co2Kg;
}
Mechanism 4 · queries

Soft delete is a convention the queries carry

There is no global filter. Every read spells out AndDeletedAtIsNull or AND a.deletedAt IS NULL, and a delete is an update that stamps deletedAt. It is explicit by design, but it means a new query that forgets the clause will silently return deleted rows.

// DELETE /api/activities/{id} — ownership check, then a soft delete
if (!log.getUserId().equals(userId)) return ResponseEntity.status(FORBIDDEN).build();
log.setDeletedAt(Instant.now());
repo.save(log);
Mechanism 5 · environments

Docker locally, Cloud SQL in production

Local development runs postgres:16-alpine from database/docker-compose.yml, with a named volume and a pg_isready healthcheck. In production the same code reaches Cloud SQL through postgres-socket-factory, so the only thing that changes is the value of DB_URL — supplied by Cloud Run from Secret Manager.

# one-time local setup
docker compose -f database/docker-compose.yml up -d
# Flyway runs on backend boot; demo data is optional
psql -h localhost -U ecotrack -d ecotrack -f database/seed.sql
Why this split matters

Because ddl-auto is none, adding a field to an entity does nothing to the database. A schema change is always two commits' worth of work: a new Vn__*.sql migration and the matching entity field. Skip the migration and you get a column-not-found error at query time, not at startup.

04 — identity

Auth, end to end

Stateless on the server. The only auth state in Postgres is a table of hashed refresh tokens.

Two tokens, two lifetimes

Login returns a short-lived access token and a long-lived refresh token. The access token lives only in a module variable — a tab refresh loses it on purpose. The refresh token persists in localStorage under cx-refresh, and its hash is the row in refresh_tokens.

  • Access token — 900s, JWT_ACCESS_TTL, carries sub / email / role
  • Refresh token — 14 days, rotated on every use
  • Passwords — BCrypt via PasswordEncoder
  • Google sign-in — GoogleTokenVerifier validates the ID token against GOOGLE_CLIENT_ID

The 401 that heals itself

apiFetch retries exactly once. On a 401 it refreshes, replays the original request, and only redirects to /login if the refresh itself fails. The client module rehydrates the refresh token at import time, so a hard navigation after login does not break that recovery.

if (res.status === 401 && retryCount === 0) {
  const refreshed = await refreshAccessToken();  // mutexed
  if (refreshed) return apiFetch<T>(path, options, retryCount + 1);
  clearTokens();
  window.location.href = '/login';
}
05 — the seams

What is swappable, and where values live

Two deliberate constraints shape the backend: no cloud SDK is called directly from a service, and no business number is hardcoded in Java.

Every external service sits behind an interface

Services depend on the interface; the implementation is chosen by a config value at startup. This is also what lets the whole app run offline — the stub and canned paths need no Google credentials at all.

AIProvider──► GeminiAIProvider · CannedFallbackProvider  AI_PROVIDER
OcrProvider──► GoogleVisionOcrProvider · Tesseract  OCR_PROVIDER
BlobStorageService──► GoogleCloudStorageService · local_stub  STORAGE_PROVIDER

Highlighted values are the defaults in application.yml. AI_FALLBACK=true means a Gemini timeout degrades to canned output rather than failing the request.

Three layers of configuration

Each layer overrides the one before it, and the last layer is editable without a redeploy.

application.yml   ← committed defaults
      ↓
environment vars  ← Cloud Run + Secret Manager
      ↓
app_config table  ← runtime-editable, no restart

Business values are rows, not constants

Emission factors, credit rules, AI prompt templates, the rewards catalogue and the action catalogue are all seeded by V3__reference_data.sql and read from the database at request time.

  • emission_factors — kg CO₂ per km / kWh / item
  • credit_rules — read by CreditRuleEngine
  • prompt_templates — rendered by PromptRenderer
  • rewards, action_templates — catalogues
